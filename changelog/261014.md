## 成本记账修复与多维归属

- 修复**流式对话不记 token** 的主因：vortexagent 的 OpenAI 兼容层在 `stream=true` 时从不发 `stream_options:{"include_usage":true}`，而多数网关不主动回传流末 usage。Friday 网页聊天总是走流式，于是 `llm.Usage` 恒为 0 → `usage.Add` 丢弃零值 →「运行状态」页的 token 数字长期不可信。框架侧补齐请求侧（解析侧本已支持），并新增 `llm.WithStreamUsage` / `ProviderConfig.StreamUsage` 作为个别网关拒收该字段时的关断门。

- 归属来自 ctx：`internal/agent/pool.go` 加 `WithOrigin/OriginFrom`、`WithRun/RunFrom`，四个入口各设一次（网页、终端、钉钉/飞书、任务回调），LLM 钩子在同一 ctx 上取用；新增 `internal/llmx/counted.go`（`llm.Provider` 三方法装饰器）只包上下文引擎的摘要器 provider，把绕过 Hooks 的归档/摘要调用计入 `origin=summarizer`——这部分此前是账本暗区。

## 计划模式（清单可审阅、用户确认后按步执行）

- 聊天选「计划」不再只是把 `【计划】` 拼在文字前面发给模型：请求体新增 `mode` 字段（`ChatView.vue` 删除前缀，后端 `HandleSSE` 解析），规划轮产出**结构化步骤清单**→ 网页计划卡 → 用户确认 → 服务端按步执行。计划模式未启用（`plan.enabled: false`）时请求被明确拒绝并说明原因。
- 规划轮用框架的 `WithJSONMode()` 要结构化输出，并配一份**内置规划技能**（`allowed-tools` 只给读类工具：`get_time/list_todos/get_weather/list_files/read_file/recall/search_history`）：既要 JSON 又不许下手改数据。为此给 `Brain` 加 `WithInlineSkill`（内存技能，不进用户可编辑的仓库）。解析失败追加一次纠正提示重试（沿用 ctxengine 摘要器"一次纠正"的先例），仍失败就**降级为普通回答**并把模型原话返回——不留一张点了没反应的死卡片，同时落一条 `failed` 计划说明原因。
- 为什么一步一问：框架轮数上限是"一次 Ask 内"的，且默认只有 10 轮；把整份计划塞进一次长对话轮，一旦耗尽就是"工具副作用已发生、推理记录整轮丢失"。一步一次提问还给出天然的暂停/重试粒度，并让每步的 token 单独入账（步骤结构里带 `in/out`）。规划轮与每一步都跑在**独立会话** `plan-<id>`（决策：不占用 `web` 主会话的 per-key 锁，用户聊天不被阻塞），成本归到账本 `byRun["plan:<id>"]`。
- 确认通道刻意**不复用危险操作的审批队列**：`approval.Queue.RequestRemember` 在 `acceptEdits/fullAccess` 档直接放行、5 分钟超时、纯内存——用它做计划确认会出现"权限模式一开就没人确认计划"的安全倒退。确认走 `POST /api/plans/:id/confirm {approve, steps?}`，允许"先改再确认"（只能改待执行步骤，数量不符直接拒绝），确认后由服务端 goroutine 执行、前端轮询 `GET /api/plans/:id`（不新建 SSE 通道：过程事件 hub 按 reqID 路由，多步多 reqID 需要第二维度，而轮询扛得住关标签页）。
- 状态机与恢复：`draft → awaiting_confirm → running → completed|failed|canceled`，`paused ⇄ running`；步态 `pending|running|done|failed|skipped`。某步失败**不阻断**后续步骤（该步标 failed + 错误，卡片给"重试/跳过"）；被暂停/取消打断的那一步退回 `pending` 而不是"失败"（它没做完，也不该要求用户重试）。重启加载时 `running → paused` 并写明"进程重启时正在执行"，`draft → failed`，在跑步退回待执行；绝不自动续跑（副作用不可知）。同一计划不可双跑（`Start` 幂等保护 + 活跃表），终态计划不能再启动。
- 预算：每轮循环在**步边界**查 `cost.budget.perPlanTokens`（读 usage 的 `byRun` 桶，与"运行状态"页同一口径），超线则 `paused` 并写明"预算已用满（x/y）"，已完成步骤不受影响；计划是用户确认过的工作，因此不吃成本软限额闸门（闸门只管心跳/智能任务/目标）。单步轮数上限走框架新加的 `WithMaxIterations`（新配置 `plan.maxIterations`，默认 12）。
- 落盘与仓库：`internal/plan`（plan/store/parse/planner/run 五个文件），`plans.json` 沿用原子写 + 损坏保留约定，保留最近 50 条（终态从最旧淘汰，进行中的永不淘汰）；`Update` 在仓库锁内改、校验失败或写盘失败**整体回退**。新配置键 `planFile`。
- 接口与前端：`internal/admin/plans.go` 提供 8 条计划路由（列表/详情/确认/暂停/继续/取消/重试步/跳过步），`admin.go` 路由一览注释同步补齐；聊天里的计划卡显示每步状态、token 与错误，按钮随状态切换（待确认→确认执行/先不做；执行中→暂停；暂停→继续/取消；失败步→重试/跳过），执行期 2.5s 轮询自身状态、终态即停表。

## 目标模式（一条带预算的长程自主任务）

- 目标**不新建存储**：它就是带 `goal: true` 的 `KindAgent` 任务，落在同一个 `tasks.json`。这样排程、原子落盘、重启补偿、暂停/编辑/取消、通知中心投递全部免费复用，也避免"两处真相"。meta 键沿用 `metaHeartbeat` 的写法（`metaGoal/metaGoalMaxSteps/metaGoalMaxTokens/metaGoalSkill`），`toTask` 加载时校验（目标必须是智能任务、预算非负），校验失败保留原文件并报错而不是静默丢弃。
- 模型自己也能建目标：`schedule_task` 工具参数与 schema 扩 `goal/maxSteps/maxTokens/skill`。
- `internal/agent/goal.go` 的 `GoalRunner` 是执行体：并发槽（`cost.goals.maxConcurrent`，默认 1——目标轮次长、成本大）+ 活跃表防止同一目标双跑（第二次触发明确记一条"跳过"轨迹），生命周期挂应用 ctx 而非 HTTP 请求，会话隔离为 `goal-<id>`。步循环在**步边界**查两道闸：成本软限额与本目标累计 token（读账本 `byRun["goal:<id>"]`，与"运行状态"页同一口径）；单步轮数上限走框架 `WithMaxIterations`。
- 推进协议 `[达成]/[受阻]/[继续]`：单步失败**不判死**，把失败原因带进下一步继续试；最后一步仍在推进时，把它的进展作为"告一段落"的结论返回（比空手收尾更有信息量）。只有**达成**才打扰用户，受阻/超预算只留轨迹——避免半夜反复推送坏消息。停止是软停：当前这一步跑完就停，已产出的结论仍会送达。
- 刻意**不用**框架的 `agent.TaskHub`（它要求 `Register(name, *Agent)` 并自己跑 `Agent.Ask`，会绕过 Friday 的 Brain：自定义指令、技能、权限桥接、trace、usage 归属全丢），也不直接用 `autonomous.AutonomousAgent`（Friday 已把它包成排程器，`UserInputCh` 未接线）。投递沿用心跳的"决策与投递分离"：`Prepare` 出结论、`deliver` 走通知中心，于是免费得到可靠入队、`processing→pending` 恢复、失败 5 次重试与通道去重。
- 聊天里选「目标」= `LaunchGoal`：落成"几秒后的单次 agent 目标任务"，零模型调用先回一句确认，执行仍走与定时目标完全相同的 Resolver → `GoalRunner.Prepare` 路径，因此重启后这条目标也还在。
- **实现偏离计划一处**：原计划在 `trace.Request` 加 `Group` 字段 + `ListByGroup` 来做目标/计划的轨迹分组；实际改用已有的 `session` 维度（`GET /api/traces?session=goal-<id>`）。会话 key 本来就按目标隔离，加字段要动旧 `traces.json` 的兼容语义却不带来新信息。新增的条目类型只有 `goal_run/goal_step/budget/skill`（`format.js` 的 `EV_TITLE` 与 `style.css` 的 chip 配色补齐 `skill/plan_step/goal_run/goal_step`，并新增 `web/tests/trace-titles.test.js` 盯住"后端加了条目、前端忘登记就显示裸 key"这类回归）。
- 接口与前端：`internal/admin/goals.go` 提供 `GET /api/goals`、`GET /api/goals/:id`（含该目标最近轮次）、`POST /api/goals/:id/stop`，其余 CRUD 走 `/api/tasks`；「自动化」页在勾了"智能任务"后才出现"目标"复选框，勾选展开步数上限/Token 预算/技能三项，卡片加 `目标` 徽标与 `x / y tokens` 明细，按钮"查看执行轮次"（跳轨迹页并按会话过滤）与"停止这次推进"。没加新页签，也没加新轮询循环（进度并入既有的 `refreshAll`）。
- 收尾补上计划里列的义务：`GoalSessionKey(id)` 统一会话 key 口径（**空 ID 必须返回空串**——`Brain.Reset("")` 会落到默认网页会话，等于误清用户对话），`Brain.ReleaseGoalSession` 在取消目标时释放内存会话并清其轨迹（`SessionPool` 只增不减，不释放就随目标数量线性膨胀）；目标仍在推进时跳过，因为清会话要等当前这一步结束、会把取消请求挂住几分钟。
