## feat(界面): 头部速率改为两态——回答中实时 tok/s，空闲回落会话平均

- 时间: `2026-11-10`

### 变更内容

会话头部的 `↓N tok/s` 改为两态：回答进行中显示流式实时速度（复用既有滑动窗口估算，与时间线角标同源），一轮结束/空闲时回落到会话平均吞吐（ΣOut/ΣMs，轮末更新）。缓存命中保持会话口径不变（只有轮末数据）。

### 修改原因

用户期望头部是实时速度；此前头部只有轮末才会更新的会话平均，实时值藏在时间线角标里。

### 实现方式

`WorkspaceView` 新增 `headRate` computed：`generating(current)` 时从 `states[current.id].messages` 倒序找流式 bot 消息的 `rate`（`feedRate` 滑动窗口值），否则取 `current.outRate`。头部模板统一吃 `headRate`，title 说明两态口径。补测试覆盖两态（实时值不定数用正则断言，回落值精确断言）。

### 涉及文件

- `web/src/components/WorkspaceView.vue`
- `web/tests/workspace-view.test.js`

## feat(界面): 会话头部显示输出速率与缓存命中率，列表累计 tokens 撤下

- 时间: `2026-11-10`

### 变更内容

会话页头部（状态词之后）插入两个统计段：`↓385 tok/s · 缓存命中 99.8%`。速率是会话累计输出 tokens ÷ 累计整轮耗时（含工具调用，整轮吞吐口径，实时流式速度仍在时间线角标）；命中率 = 缓存读 ÷（缓存读+缓存写+输入），只统计 agent 上报过缓存读的轮次——没报就不占位，不装作有数。同时撤掉上一条刚加的「会话列表行累计 tokens」（用户要的是速度与命中率，不是累计量）。

### 修改原因

ACP 的 `PromptResponse.Usage` 自带 `CachedReadTokens/CachedWriteTokens`，此前解析时丢掉了；会话头部一行放得下这两个高频关注的数字。

### 实现方式

`TurnResult`/`Entry` 增加 `CacheRead/CacheWrite`（从 Usage 指针字段安全解引）；`Thread` 头部统计改为 `OutRate/CacheHit`（`headStats` 在 List/Get 响应副本现算，不落盘）；桌面头部模板接 `fmtRate`（≥100 取整）与百分比；`TestThreadHeadStats` 覆盖「未上报缓存 → 命中率为 0」与「按上报轮次计 990/1010」。

- `internal/acp/manager.go`
- `internal/acp/manager_test.go`

- `web/src/mobile/MobileThreads.vue`

## feat(界面/移动端): 会话列表行显示累计 tokens

- 时间: `2026-11-10`

### 变更内容

工作区会话列表（桌面分组行、「最近更新」行、手机项目会话行）的副标题在 agent 与时间之间插入累计用量，点分段：`zcode · 1.5k tokens · 刚刚`。没记上量的会话（旧数据或内置会话零值）不占位。

### 修改原因

tokens 计量此前只在「设置 → 运行观测 / 成本与预算」和内置聊天轮末汇总里有，智能体会话列表看不到每条会话烧了多少；投影里逐轮 In/Out 本来就存着，列表直接可用。

后端 `Thread` 增加 `tokensIn/tokensOut`（omitempty），`List()`/`Get()` 在响应副本上用 `sumTokens` 从逐轮 Entry 现算——不落盘、不存总量，避免与消息列表漂移；前端无需新接口。前端 `tokensMeta` 助手复用 `fmtTokens` 缩写，桌面 `WorkspaceView` 两处行与移动端 `MobileThreads` 行共用同一格式。Go 侧补 `TestThreadTokenTotals`。

## 智能体用量：按 adapter 能力取数（白名单）+ 头部统计口径修正

### 变更内容

会话头部 `↓tok/s`/`缓存命中` 的取数改成按 agent 能力分流，并修掉两处口径问题：

1. 新增 `internal/acp/usage_caps.go`：记录哪些 agent 的用量不在标准
   `PromptResponse.Usage` 里（目前只有 codebuddy-code 走 `usage_update._meta.usage`），
   以及 2026-11-10 各家 adpater 的实测结论。
2. codebuddy-code 从 `usage_update._meta.usage` 累加真实用量（按 messageId 去重，
   一轮多次模型调用求和），输入按「未命中缓存」口径记录，缓存读写一并带上。
3. `headStats` 跳过没上报用量的轮次（取消/报错）：此前这些轮只把耗时计进分母，
   会把平均值稀释到接近 0。
4. 前端头部速率在回答中暂时没有文本增量时回落到会话平均，不再整段消失。

### 修改原因

用户反馈同一台机器上「tok/s 时有时无」。实测原因分两类：一是各 adapter 上报
能力差异极大（codebuddy-code / minimax-code 的 prompt 响应完全没有 usage），
二是 codex 的取消轮没有 usage 却计入了耗时分母，平均值被拉到接近 0。

### 实测结论（本机 adapter 版本）

| agent | 响应级 usage | _meta.usage | 缓存字段 |
|---|---|---|---|
| codex (codex-acp 2.2.2) | ✅ | — | cachedRead/WriteTokens |
| zcode (zcode-acp-server) | ✅ | — | cachedRead/WriteTokens |
| codebuddy-code (2.179.3) | ❌ | ✅ | prompt_cache_hit_tokens |
| minimax-code (0.7.4) | ❌ | ❌（只有 used/size/cost） | ❌ |
| claude (0.16.1) | ❌ | ❌ | ❌ |
| opencode | ❌（该版本 acp 是 HTTP 服务） | ❌ | ❌ |
| gemini | 未验证（需要登录态） | — | — |

### 实现方式

`newTurnSink` 按 agent name 取 `usageCaps`；只有白名单里的 agent 才解析
`usage_update._meta`（非标准扩展，不能对所有 agent 默认开）。轮末优先用
`PromptResponse.Usage`，为空时回落到本轮累加的 meta 用量。`headStats` 对
in/out/缓存全为零的轮次直接 `continue`。

## fix(智能体): qoder 拿不到模型——握手后补做 authenticate

- 时间: `2026-11-10`

### 变更内容

qoder 接入后模型选择器一直是空的。根因是 qoder 1.1.x 的 ACP 把「登录态」与「模型清单」绑在 `authenticate` 上：客户端不显式调用它，`session/new` 照样成功，但 `models.availableModels` 与 `configOptions` 里的 model 全是空数组。现在 `acp.agents[]` 新增可选 `authMethod`，有值时在 initialize 之后、建会话之前调用一次 `authenticate`；设置页 agent 卡片也加了「预认证方法」输入框。

### 实现方式

`spawnAgent` 握手成功后按 `cfg.AuthMethod` 调 `conn.Authenticate`，超时 1.5s 后放行——qoder 收下请求却不回响应（实测等不到 result），但服务端在 0.5s 内已生效，能否干活仍由随后的 `session/new` 判定；非超时的错误只记日志、不阻断。空值保持旧行为（不调用）。实测 qoder 1.1.83：不调用时 models=0，调用 `qodercli-login` 后 models=15、model 选项 15。

另：本机 `~/.zshrc` 里失效的 `QODER_PERSONAL_ACCESS_TOKEN` 已注释——它优先级高于已保存登录，会让 `session/new` 直接报 `Authentication required`。

### 涉及文件

- `internal/config/acp.go`
- `internal/acp/proc.go`
- `web/src/components/settings/AcpSection.vue`
