## fix(审批): 审批/提问卡按会话归属，不再在任意页面弹出（`0d7c872`）

- Commit: `0d7c872`
- 时间: `2026-11-09`

### 变更内容

审批卡与 agent 提问卡现在会带上所属会话（聊天 / 工作区的某条会话）。只有「当前正在看的那条会话」的卡片才就地展开；其他会话的卡收进右上角的「N 个待处理」提示，点开后按会话列出，点一条自动跳到对应会话再处理。

### 修改原因

用户反馈「agent 的审批无论我在哪个页面都会弹出来，导致我无法知道到底是哪个窗口的 agent 在申请」；提问也一样。

### 实现方式

审批队列 `Item` 增加来源字段（source/threadId/threadTitle/agent，JSON 平铺）。外部 agent 在 `request_permission` 入队时直接带 thread；内置 Friday 在工作区里跑时只有 ctx 里的 `acp-<会话 id>`，装配时注入 `OriginResolver` 反查回 thread；`write_file`/`edit_file`/`mcp_edit` 改走 `RequestCtx`，同一套来源解析。前端 `ApprovalCards` 按 `store.view` 与 `store.acpCurrentThread` 判断卡片归属：不属于当前会话的移入右上角提示，点击时切到对应模式并设置 `acpOpenThread`；工作区把当前会话同步到 `store.acpCurrentThread`。

## feat(通知): 通知中心支持全部已读（`b99e971`）

- Commit: `b99e971`
- 时间: `2026-11-09`

### 变更内容

通知页顶部新增「全部已读（N）」按钮，一次把当前所有可见未读标为已读，并同步刷新侧栏未读数。按钮在没有未读时置灰。

### 修改原因

用户反馈通知页面缺少「全部已读」入口，只能逐条点。

### 实现方式

新增 `POST /api/notifications/read-all`，`Center.MarkAllRead()` 只处理「已准备结果且需要推送」的通知（与 `Unread()` 同口径），一次落盘；保存失败回滚内存状态，避免界面已读、磁盘仍未读。前端按钮走同一 REST，成功后重新拉取列表。

## fix(桌面): 应用在前台时也弹系统通知横幅（`1e894e6`）

- Commit: `1e894e6`
- 时间: `2026-11-09`

### 变更内容

macOS 系统通知在应用处于前台时也会在右上角弹出横幅；点击横幅会把主窗口叫回前台并切到通知页。

### 修改原因

用户反馈「系统级别的通知没有生效，右上角没有任何的横幅提示」。排查后确认通知请求本身已被系统接受（`desktop-notifications.json` 里有 accepted 记录），但 macOS 在应用激活时默认只把通知放进通知中心、不展示横幅，除非实现 `UNUserNotificationCenterDelegate` 的 `willPresent` 并明确返回展示选项。

### 实现方式

桌面外壳用 `objc2` 定义 `UNUserNotificationCenterDelegate`，`willPresent` 返回 `Banner | Sound | List`；委托是弱引用，泄漏到进程结束保证一直生效。`didReceive` 里唤起主窗口并 emit `friday:notice-click`，前端监听后切到通知页；`main-kernel` 能力补 `core:event:default` 允许内核页面监听该事件。

- `desktop/src-tauri/capabilities/main-kernel.json`

## feat(智能体/终端): 终端不限数量、CodeBuddy 会话独立进程、删除并发上限（`80af34d`）

- Commit: `80af34d`
- 时间: `2026-11-09`

### 变更内容

四件事：内置终端默认不再限制同时开启数量；MiniMax 问答后卡死时自动重建连接继续对话；CodeBuddy 默认每会话独立进程，同项目多会话不再串行；`acp.maxConcurrent` 配置项与槽位/排队机制整体删除。

### 修改原因

- 内置终端原先最多 4 个，用户要求去掉。
- MiniMax 0.7.4 的 `ask_user` 答复后 ACP 桥已 `end_turn`、runtime 却停在 `waiting-for-user`，后续消息被 busy 拒绝；此前只做 `session/cancel` + 重发，而挂起态不认 cancel，仍然接不上。
- CodeBuddy 2.179.3 的 ACP 每条连接只有一条 prompt 渲染循环（`activeRenderConnections` 按 connectionId 去重，循环体串行 await），Friday 的「agent + 目录」复用模型让同项目多会话共连接，第二个 prompt 只能排到第一个 turn 结束。
- `maxConcurrent` 是 Friday 自加的资源闸，不是 ACP/Zed 的要求（Zed 的 `agent_servers` 只有 command/args/env），用户要求直接删除。

### 实现方式

- 终端：`DefaultMaxSessions = 0`，`Start` 仅在 `max > 0` 时判上限；前端去掉 `|| 4` 兜底。
- MiniMax：busy 自愈二次仍失败时 `killLive` 重建连接、`ensureLive` 按 `session/load` 重接，再重发同一份 prompt；`activeTurnBusy` 增认 `waiting for user input` / `cannot be continued`。
- CodeBuddy：新增 `oneSessionPerProcess`（全局 + 逐 agent 三态，CodeBuddy 按特征默认 true）；true 时复用键加 threadID，一会话一连接一进程，停止也不再连坐同项目其他会话。
- 并发上限：删除 `MaxConcurrent` 字段/常量/校验/写回、`sem` / `acquireSlot` / `releaseSlot` / `waiting` / `queueCancels` / `fastEvictIdle`、`StateQueued` 与前端排队展示；设置页移除对应输入。
